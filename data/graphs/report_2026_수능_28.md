# 드라이런 평가 — 2026 수능 미적분 28번 (정답 ⑤, 157/12 + ln 2)

## (1) 발견이 진짜인가
- 핵심 발견은 두 개다. ① "HT = s·f'(s)" (q2), ② "역함수의 적분 = 직사각형 차 − 원함수의 적분" (q4).
- ①은 진짜 캔버스 발견이다. 학생은 접선의 y절편을 식으로 계산하지 않는다. P 를 끌면 H, T, P 가 만드는 직각삼각형이 눈에 보이고,
  "기울기를 1 로 만들어라"는 지시가 t = s 가 되는 순간을 **몸으로** 찾게 한다. t/s 눈금은 체크포인트 전까지 숨겨서
  "t/s = 기울기"는 학생이 세 눈금(s, t, 기울기)을 비교해 스스로 추측해야 나온다. 종합법(접선 식 → y절편 → 뺄셈)을 뒤집은 것이 아니라,
  종합법이 숨기는 기하(삼각형)를 먼저 보게 하는 경로다.
- ②는 반(半) 발견이다. "∫g 영역 칠하기"(predict)와 "타일 조합 맞추기"(action)는 학생이 직접 하지만, 세 타일(큰 직사각형·작은 직사각형·곡선 아래)
  을 앱이 미리 골라 준 시점에서 답의 구조는 거의 정해진다. 학생이 발견하는 것은 **부호 조합**(+, −, −) 뿐이다.
  타일 없이 "영역을 직사각형과 곡선 아래 넓이로 쪼개 보라"고만 하면 더 진짜가 되지만, 체크포인트를 판정할 방법이 현재 스키마에 없다 (→ (5)).
- q1 의 "g 는 역방향 대응이니 정방향 t = h(s) 를 먼저 찾자"는 분석법의 전형적 한 수이지만, 질문 문구가 이미 답(역함수)을 말해 준다.
  이 단계만큼은 질문 트리가 "변장한 정방향 풀이"에 가깝다. 다만 이 통찰은 캔버스로 발견시키기 어렵고 '문제 이해' 영역이라 허용 범위로 본다.

## (2) 딸깍 누수
- s1: `readout_slope` 가 처음부터 열려 있다. 기울기 수치를 보면 t/s 와 비교가 쉬워져 발견이 약해질 수 있다 — 그러나 기울기를 숨기면
  "기울기 1 로 맞춰라"는 지시 자체가 불가능하다. 절충으로 t/s 만 `after-checkpoint` 로 막았다. 누수 등급: 낮음.
- s2: predict 의 `feedback_on_miss` 가 h(1)=1/2, h(3)=27/4 를 말해 버린다. 예측을 틀린 학생은 q3 의 핵심(구간 끝점 = 1, 3)을 공짜로 받는다.
  틀렸을 때 피드백을 "h(1), h(3) 을 직접 계산해 보라"로 바꾸는 편이 낫다. 누수 등급: 중간.
- s3: `readout_sum`(현재 조합의 넓이)이 항상 보이므로, 학생이 조합을 바꿀 때마다 숫자가 변해 '정답 숫자 맞추기' 게임으로 변질될 수 있다.
  단, 목표값(region_g 의 넓이)은 체크포인트 뒤에만 열리므로 무엇에 맞춰야 하는지는 모른다. 누수 등급: 낮음.
- 곡선 h 는 s2 에서 이미 열렸는데 s3 에서 다시 predict 를 요구한다. 규칙("함수는 predict 후에만")을 지키려는 형식적 반복이지,
  정보 보호 효과는 없다. 학생 입장에선 번거로움.

## (3) predict 단계가 의미 있는가
- s1 predict: f 의 개형(정의역 x>−1, 원점 통과·원점에서 기울기 0, 극값 0개, 오른쪽 증가, 왼쪽 끝 −∞). f'(x) = x²/(1+x) 를 통분해야만
  "극값이 없다"를 맞힐 수 있으므로, 예측이 곧 핵심 계산을 유도한다. 판정: `accept` 의 7개 질적 속성과 스케치 비교(sketch-matches, qualitative).
- s2 predict: h 의 개형(원점, 증가, 아래로 볼록, h(1)=1/2, h(3)=27/4). 여기서 "적분 구간 끝과 같은 수"를 예측 중에 만나는 것이 설계 의도.
- s3 predict: 곡선이 아니라 **영역**을 예측한다("∫g 는 곡선 왼쪽 영역"). 이 문항에서 가장 의미 있는 예측이다 — 역함수 적분을 넓이로
  바꾸는 전환 자체가 예측 대상이기 때문. 다만 `sketch-matches` 는 곡선 비교용이라 영역 비교를 어떻게 판정할지 미정이다.

## (4) 검산 결과 요약
- `verify_2026_수능_28.py` — 30/30 PASS. 주요 항목: f' = x²/(1+x); HT = s f'(s) = s³/(1+s); f'(s)=1 ⇔ s=(1+√5)/2;

  넓이 관계·치환적분·수치적분(13.77648…) 세 경로 모두 157/12 + ln 2; 보기 ⑤ 와만 일치. 전체 claims 는 JSON `verification` 에 삽입.

## (5) 스키마/앱 설계에 드러난 문제점과 제안
1. **체크포인트에 "영역 조합(region-compose)" 타입이 필요하다.** 이 문항의 결정적 발견(역함수 적분 = 넓이의 합·차)은 "학생이 어떤 영역들을
   어떤 부호로 골랐는가"로 판정해야 한다. 현재는 `point-in-region` 에 `requires_composition` 을 비표준 필드로 끼워 넣었다.
   제안: `{ "type": "region-compose", "target": "region_g", "tiles": {...}, "accept": {"rect_big": "+1", ...}, "area_tolerance": 1e-3 }`.
2. **predict 의 대상이 곡선만이 아니다.** s3 처럼 "영역"이나 "구간 대응"을 예측시키려면 `sketch-matches` 외에 `region-matches`(칠한 영역의
   IoU 판정), `value-matches`(h(1), h(3) 같은 수치 입력 판정)가 있어야 한다. 특히 수치 입력형 predict 가 있으면 (2)의 s2 누수를 막을 수 있다.
3. **같은 함수를 장면마다 다시 predict 하게 하는 규칙은 완화가 필요하다.** `reveal: "after-predict"` 에 `"predicted-in": "s2"` 같은 참조를
   허용해 "이미 예측한 곡선은 바로 연다"가 되어야 한다. 지금 규칙을 글자 그대로 지키면 s3 가 형식적 반복이 된다.
4. **라벨 가시성 단계가 필요하다.** 이 문항은 `reveal: "after-checkpoint"` (t/s 눈금, 목표 넓이) 없이는 설계가 성립하지 않는다.
   스키마 v0 의 reveal 값은 `after-predict` 뿐이므로 `after-checkpoint`, `after-synthesis` 를 공식 값으로 추가해야 한다.
5. **슬라이더와 점 드래그의 바인딩.** s1 에서 학생은 슬라이더가 아니라 점 P 를 끈다. `point-on-curve` 에 `binds: "s"` 를 비표준으로 넣었다.
   드래그 가능한 점이 슬라이더 값을 거꾸로 갱신하는 양방향 바인딩을 DSL 이 명시해야 Manim/JSXGraph 양쪽 렌더가 같은 의미를 갖는다.
6. **복합 체크포인트.** q3 은 "t 가 27/4 에 도달" AND "교점 개수 = 1" 두 조건이다. `and` 필드를 임시로 썼다. `all: [...]`/`any: [...]`
   조합 문법을 스키마에 넣는 것이 낫다.
7. **좌표축 이름 바꾸기.** s2, s3 는 (s, t) 평면이라 `axes: {x: "s", y: "t"}` 를 추가했다. 역함수 문제는 거의 항상 축 이름이 바뀌므로 표준 필드로.
8. **(설계 관찰)** 이 문항은 '그래프 딸깍'보다 '식 딸깍'(접선 식을 바로 써 버리는 것)이 더 큰 누수다. 스키마는 곡선 공개만 통제하는데,
   적분·접선 문제에서는 "수식 힌트를 언제 여는가"도 같은 수준으로 통제할 필요가 있다 (예: `hint` 에도 reveal 단계를).
